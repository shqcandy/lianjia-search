# 链家/贝壳房源数据方案核验与实施建议

核验日期：2026-10-06

## 结论

原设计中的字段和分层思路可作为数据整理草案，但数据获取部分不能按“登录态自建采集”直接实施。贝壳现行服务协议将“爬取贝壳房源信息”列为异常访问示例，并限制未经书面许可用机器人/蜘蛛等程序擅自获取内容，也限制自动化或抓取数据行为；协议保留限制在线沟通功能及封禁账号等处置权。低并发、随机等待、复用 Chrome Cookie 都不能消除该风险；代理轮换或验证码处理会进一步偏离安全边界。

已发现贝壳技术团队发布的官方 `beike-ai-platform` CLI，README 展示二手房搜索命令，使用前需要登录取得 API Key，并注明“商业软件，仅限授权用户使用”。因此，原文“没有公开 REST API”不应直接等同于“完全没有官方可用的数据查询渠道”：应先确认本人是否属于授权用户、CLI 服务条款及搜索结果字段/完整性是否满足要求。它不是无需授权的公共 API，也不能据 README 推断可全量导出。

若没有获准使用且覆盖所需字段的数据源，则停止自动采集，改成人工站内查询与手工记录，或更换获得授权的数据提供方。不能把第三方托管爬虫当作授权证明。

## 需求口径需要先固定

- 城市/行政区：北京、海淀区。
- 楼龄：以当前日期 2026-10-06 计算，“10年以内”按建成日期不早于 2016-10-06；若来源只有建成年份，则采用 2016 年及以后，并在结果中标记这是年份级近似。
- 总价：300 万至 500 万元，边界包含。
- 电梯：必须以房源级明确字段为准；小区级“电梯占比”不能代替单套房源判断。
- “大产权房”：当前方案没有可验证的数据字段或判定定义。实施前需由需求方确认是指商品房/可上市交易住宅，还是另有产权口径；不能用“商品房”标签未经核实地代替。
- “所有类型”：建议解释为不限定户型、楼型或住宅类型；仍只查询二手在售住宅。需要确认是否包括商住、公寓、别墅等非普通住宅。
- “所有小区/所有在售房”：只有来源能证明完整分页、未隐藏/延迟房源、且提供可审计的更新时间时才能承诺。否则结果只能称为“来源当前可见结果”，不能声称全量。

## 原方案修订

1. **不实施 Fetcher、Cookie 会话复用、代理、并发/随机延迟或验证码处理。** 这些并不能保证账号安全；检测到登录墙、验证码、访问限制或协议禁止时必须停止，不重试、不切换身份或 IP。
2. **先走授权渠道核验。** 向贝壳官方开放平台或商务渠道书面确认：北京二手房范围、海淀过滤、分页/总数、建成年份、电梯、产权性质、在售状态、更新时间、导出/留存权利，以及个人/内部分析使用限制。确认后才决定适配器和存储方式。
3. **做无采集的字段验收。** 用授权文档、官方演示数据或人工查看的少量样例填写字段映射表；不要自动化访问已登录 Chrome。样例只用于判断字段是否存在，不能据此宣称全量。
4. **若获授权数据源可用，采用最小实现。** 单次手动触发的导入/查询 + 标准化过滤 + CSV/XLSX 两个工作表（小区汇总、房源明细）即可。SQLite、调度器、历史价格、FastAPI、断点续跑均非首版必需；只有确认需要长期增量运行后再加。
5. **若没有授权数据源，止步于人工辅助表格。** 可以由用户在站点界面正常搜索并手工导出/录入允许使用的数据；不要用浏览器自动化、DOM 抓取或网络接口逆向来“补全”。

## 建议验收标准

- 每条房源有来源、采集/查询时间、房源标识（仅在授权允许保存时）、小区名、总价、建成年份/日期、电梯、产权判定及原始字段依据。
- 过滤边界测试：300 万与 500 万均保留；超过边界排除；未知楼龄、电梯或产权状态进入“待核实”，不得静默当作符合。
- 小区列表按符合条件房源反向汇总；无符合房源的小区不列入结果，除非用户明确要求列出空小区。
- 若来源不给全量/总数/更新时间保证，输出标题注明“截至查询时间的来源可见数据，非全量保证”。
- 不采集经纪人姓名、电话等个人信息；不保存登录 Cookie、验证码、设备标识或无关页面原文。

## 风险与限制

即使使用用户本人已登录的浏览器，自动化访问仍可能违反站点规则并引发账号限制；“慢一点”不是合规或防封措施。此次核验没有操作浏览器登录会话，也没有发起页面采集。现有仓库没有应用代码，因此这是方案核验与实施顺序，不是已验证的数据抓取实现。
